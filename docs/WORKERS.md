# Web Workers — the studio's main-thread shield

Everything heavy on the browser side belongs in a worker. That is
the standing rule for Holoflow Studio, and this folder is the
plumbing the rest of the site hangs off.

## Why this exists

The main thread does layout, paint, input handling, scroll, and
JavaScript. If our JavaScript eats more than one frame at 60fps
(roughly 16ms) the cursor stutters and the page feels broken.
Users notice instantly — they cannot articulate it, they just
say "this site is slow".

The fix is not "make the code faster". The fix is "move the code
off the thread that owns the cursor". Web Workers run in their
own thread with their own JavaScript heap. They cannot touch the
DOM, which is the whole point — they are sandboxed compute.

We use them for:

- Building the search index over a few thousand entries.
- Parsing RSS / Atom feeds when the /feed page aggregates 30+
  sources at once.
- Decoding `.splat` / `.ply` byte buffers before the Spark.js
  renderer takes over on the main thread.
- Anything else that would stall the cursor for more than a
  frame. If you are unsure, profile first; the answer is usually
  yes.

## The registry pattern

`lib/workers/registry.ts` is a singleton manager. Each worker
module is lazily instantiated on first use and reused for the
lifetime of the page. On `pagehide` (covers tab close, bfcache
eviction, navigation away) every live worker is terminated so
we do not leak threads across pages.

You never call `new Worker(...)` directly from product code.
You go through the wrapper, which goes through `getWorker(kind)`,
which goes through the registry's factory map.

```text
[product code] → wrapper (typed) → callWorker(...) → getWorker(kind) → Worker instance
```

The registry knows about every worker by name (the `WorkerKind`
union in `lib/workers/types.ts`). Adding a new worker means
appending one entry to the union and one entry to the factory
map. That is the whole ceremony.

## The envelope protocol

Every message in and out of a worker is shaped like this:

```ts
// Main → worker
type WorkerRequest<K, P> = { id: string; kind: K; op: string; payload: P };

// Worker → main
type WorkerResponse<K, R> = { id: string; kind: K; result?: R; error?: string };
```

The `id` is a UUID generated by `callWorker`. The client awaits
the matching response by id, which means many concurrent calls
multiplex over the same Worker instance without stepping on
each other. The worker just has to echo the id back.

`op` lets one worker handle multiple verbs. The search-index
worker handles both `"build"` and `"search"` because the index
is stateful and lives in the worker. The feed-parse worker only
has `"parse"`. Pick the granularity that suits the work.

Errors come back as `{ id, error: string }` because Error stacks
do not round-trip cleanly through the structured-clone algorithm
on every browser.

## How to call a worker from a page

Use the typed wrapper, not `callWorker` directly. The wrappers
exist so callers do not need to know the op names or the payload
shapes.

```ts
import { buildSearchIndex, searchEntries } from "@/lib/workers/search-index";

await buildSearchIndex(allEntries);
const hits = await searchEntries("aura test chamber", 10);
```

```ts
import { parseFeed } from "@/lib/workers/feed-parse";

const xml = await fetch(url).then((r) => r.text());
const feed = await parseFeed(xml);
```

```ts
import { parseSplatBuffer } from "@/lib/workers/splat-decode";

const bytes = new Uint8Array(await fetch(url).then((r) => r.arrayBuffer()));
const buffers = await parseSplatBuffer(bytes, "splat");
// ← `bytes` is now detached. Do not read it again on the main thread.
```

The default timeout is 30 s. Pass a tighter `timeoutMs` in
`CallWorkerOptions` for UI-blocking work (the search wrapper
uses 5 s, for example).

## Transferable objects (the cost-free handoff)

The structured-clone algorithm copies every byte across the
worker boundary. For a 100 MB splat file that costs ~50 ms on
a desktop and over a second on a mid-range phone. The fix is
the transferable-object protocol: hand the buffer over by
pointer, and the sender's view becomes detached.

`postMessage(message, transfer)` takes a second array of
`Transferable` objects (ArrayBuffer, MessagePort, ImageBitmap,
OffscreenCanvas, ReadableStream, WritableStream). After the
call, the originals on the sending side are detached — touch
them and the runtime throws.

The `callWorker` helper accepts a `transfer` option for this.
The splat-decode wrapper uses it for the inbound buffer, and
the worker uses it on the response so the result typed-arrays
travel back without a copy too:

```ts
return callWorker(
  "splat-decode",
  "parse",
  { format, bytes: buffer },
  { transfer: [buffer] },
);
```

Use this any time the payload is more than a few hundred
kilobytes of binary data.

## Adding a new worker — the template

1. Pick a kebab-case name, e.g. `"thumbnail-extract"`.
2. Append it to `WorkerKind` in `lib/workers/types.ts`.
3. Create `lib/workers/thumbnail-extract.worker.ts`. Skeleton:

```ts
/// <reference lib="webworker" />

import type { AnyWorkerRequest, WorkerResponse } from "./types";

self.onmessage = (e: MessageEvent<AnyWorkerRequest>) => {
  const { id, kind, op, payload } = e.data;
  if (kind !== "thumbnail-extract") return;

  try {
    if (op === "extract") {
      const result = doTheWork(payload);
      const reply: WorkerResponse<"thumbnail-extract", typeof result> = {
        id,
        kind: "thumbnail-extract",
        result,
      };
      (self as DedicatedWorkerGlobalScope).postMessage(reply);
      return;
    }
    throw new Error(`unknown op "${op}"`);
  } catch (err) {
    const reply: WorkerResponse<"thumbnail-extract", never> = {
      id,
      kind: "thumbnail-extract",
      error: err instanceof Error ? err.message : String(err),
    };
    (self as DedicatedWorkerGlobalScope).postMessage(reply);
  }
};

export {};
```

1. Register it in `lib/workers/registry.ts`:

```ts
"thumbnail-extract": () =>
  new Worker(new URL("./thumbnail-extract.worker.ts", import.meta.url), {
    type: "module",
    name: "holoflow:thumbnail-extract",
  }),
```

1. Create the typed wrapper `lib/workers/thumbnail-extract.ts`
   that calls `callWorker(...)` with concrete types.

The Next 15 + Turbopack worker URL form is
`new Worker(new URL("./name.worker.ts", import.meta.url), { type: "module" })`.
The URL literal at the call site is what lets Turbopack find
and bundle the worker file. Do not interpolate, do not pass a
variable, do not use a third-party loader. Just the literal.

## When NOT to use a worker

- Sub-16ms work. The structured-clone hop plus the postMessage
  round-trip costs ~1 ms minimum. If your function takes 2 ms,
  shipping it to a worker is a net loss.
- Render loops. Anything inside `requestAnimationFrame` that
  needs the main thread's WebGPU / WebGL / Canvas context stays
  main-thread. The splat-decode worker handles the data parse
  stage only — Spark.js renders on the main thread because it
  owns the GPU context.
- DOM mutations. Workers cannot touch the DOM. Period.
- Calls that need access to module-scoped main-thread state.
  The worker has its own JS heap; nothing crosses except what
  you postMessage.
- One-shot work that only runs once per session and never
  blocks the user (e.g. an analytics fire-and-forget). It is
  not worth the worker file and the build-time cost.

## File map

```text
lib/workers/
  types.ts                   — envelope + WorkerKind union
  registry.ts                — singleton manager, lifecycle
  client.ts                  — generic callWorker helper
  search-index.worker.ts     — MiniSearch over entries
  search-index.ts            — typed wrapper
  feed-parse.worker.ts       — feedsmith RSS / Atom parse
  feed-parse.ts              — typed wrapper
  splat-decode.worker.ts     — .splat / .ply binary parse stage
  splat-decode.ts            — typed wrapper
  particle-init.worker.ts    — TSL particle field seed (custom protocol)
  particle-init.ts           — wrapper (owns its own singleton for now)
lib/type3d/
  font-mesh.worker.ts        — 3D type geometry off-thread
```

Two of the registered workers — `particle-init` and `font-mesh` —
were authored by parallel agents under slightly different
conventions. `particle-init` uses its own message shape and owns
its own singleton (slated to migrate to `callWorker` once it
needs multi-call multiplexing). `font-mesh` lives next to its
consumer in `lib/type3d/` rather than under `lib/workers/`. Both
are reachable through `getWorker(kind)` so a future migration
does not need a registry shuffle.

Keep each file under 300 lines. If a worker grows past that,
split its helpers into a sibling `name.worker.helpers.ts`.
