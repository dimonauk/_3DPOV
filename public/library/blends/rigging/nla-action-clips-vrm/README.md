## What this teaches

How to wrap each VRM shape-key expression in its own `bpy.data.Action`, push
it to the NLA editor as a named strip, and export the result as a GLB where
each strip becomes a separate, independently-addressable glTF Animation.

Three.js `AnimationMixer.clipAction( clip )` addresses the clips by name.
VRM 1.0 runtimes use exactly this model to blend blink + smile + phoneme
simultaneously at fractional weights in real time — without the clips
interfering with each other.

## Key technique

Shape key animation data belongs to `obj.data.shape_keys` (a `bpy.types.Key`
object), not to `obj` itself. Setting `obj.animation_data.action` drives
location / rotation / scale — the shape key sliders are unaffected. The
F-curve `data_path` format for a shape key value is:

```python
f'key_blocks["{key_name}"].value'
```

relative to the Key object. Each action must be pushed to the NLA via
`shape_keys.animation_data.nla_tracks.new()` and
`track.strips.new(name, start_frame, action)`.

Clearing `shape_keys.animation_data.action = None` before export prevents
the active action from overriding the NLA strips in the exported GLB.

---

## glTF animation mode

`export_nla_strips=True` causes the Blender glTF exporter to write each NLA
strip as a separate glTF Animation with the strip name as its `name` field.
In Three.js:

```js
const clips = gltf.animations;  // [{ name: "blink_L" }, { name: "happy" }, ...]
const action = mixer.clipAction( THREE.AnimationClip.findByName( clips, "blink_L" ) );
action.play();
```

Morph target incompatibility with Draco remains (same as the shape-keys
tutorial): both `export_apply=False` and no Draco compression are required.
